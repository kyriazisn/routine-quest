## Deviation from the wireframes: onboarding order

Approved order was O1 → O2 → O3 → O4 → O5. Implemented: **O1 → O5 → O2 → O3/O4**.
Reason: the device claim code is issued per child (`POST /v1/children/{id}/claim-codes`), and the
code must be sent to the device over BLE *before* Wi-Fi is applied, because the BLE session ends
when provisioning completes. So the child must exist before pairing. No screen content changed.

## Device provisioning (Web Bluetooth)

`src/provisioning/` is a from-scratch client for ESP-IDF v5.3 `wifi_provisioning` as used by
`firmware/main/net.c`:

- `transport.ts` — BLE GATT (service `1775244d-…`, endpoints found by the 0x2901 user-description
  descriptor, fallback to the `1775ffXX` UUIDs) and an HTTP transport (simulator/tests).
- `sec1.ts` — Security 1: X25519 + SHA-256(PoP) XOR, AES-256-CTR with **one continuous keystream**
  for both directions (WebCrypto; keystream offset tracked across messages).
- `messages.ts` / `protobuf.ts` — minimal protobuf for the session, `prov-config`, `prov-scan`
  messages (field numbers from the ESP-IDF v5.3 `.proto` files).
- `provision.ts` — flow: proto-ver → session → scan → `rq-claim` (claim code) → set config → apply
  → poll status (`auth_error` / `network_not_found` mapped to UI messages).

Wi-Fi credentials go only to the device, encrypted end-to-end; they never reach the backend.

### Verification chain

1. `app/e2e/sim/prov_sim.py` implements the device side from the vendored ESP-IDF protos.
2. `app/e2e/sim/check_with_esp_prov.sh` runs Espressif's **official** `esp_prov` against the
   simulator (correct PoP → success with custom data; wrong PoP → failure). ✅
3. `npm test` runs the TypeScript client against the simulator (10 tests, incl. wrong PoP, wrong
   password, unknown SSID, 25-message keystream sync). ✅
4. `npx playwright test` runs the whole parent journey in Chromium against the real backend and
   the simulator (HTTP transport via the dev-only `?sim=` hook). ✅
5. **Not yet verified: the BLE transport on a real device** (GATT discovery, MTU, write/read
   timing). Phase 7 test plan item; needs hardware.

The `?sim=<url>` hook is compiled in only when `VITE_ALLOW_SIM=1` (e2e build). Production builds
must not set it.

## Platform limits

- **iOS/iPadOS Safari has no Web Bluetooth.** Pairing needs Chrome/Edge on Android, Windows, macOS,
  Linux or ChromeOS. iOS parents can use the app for everything else once a device is paired
  (pair from another device, or a second parent's Android). A native/BLE fallback is out of MVP.
- **Web Push on iOS** works only for an installed (Home Screen) PWA, iOS 16.4+. The O2 screen
  detects this (`push.ts` → `needs-install`) and shows install instructions.
- Service worker caches only the app shell and hashed assets; `/v1/*` is never cached.

## Security notes

- Session: HttpOnly cookie `rq_session` set by the backend; the app never sees tokens.
- API is same-origin (`/v1` proxied by Vite in dev/preview; same host behind the reverse proxy in
  production), so no CORS credentials are needed.
- Account deletion requires typing «ΔΙΑΓΡΑΦΗ» (backend enforces the same literal).
- Push payload contains only nickname + quest/reward name (docs/09).
